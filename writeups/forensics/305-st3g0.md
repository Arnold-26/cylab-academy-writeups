# 305 — St3g0

**Événement** : picoCTF 2022 · **Catégorie** : Forensics

## Énoncé

« Téléchargez l'image et trouvez le flag. » Le fichier fourni s'appelle `pico.flag.png` et affiche une image anodine comportant le texte « PICO » — aucun flag visible à l'œil.

## Analyse

PNG et indice « st3g0 » : stéganographie dans les **bits de poids faible** (LSB) des pixels. L'ordre de lecture et le canal utilisé doivent être déterminés ; tester à la main (`zsteg` sans option, `stegsolve`) peut échouer et faire perdre du temps.

Un premier essai avec un décodeur LSB en ligne ne donne rien : ces outils n'essaient qu'une combinaison, souvent `b1,rgba,lsb,xy` sur quatre canaux, alors que l'image encode le message sur trois canaux (RGB, sans alpha) — d'où l'échec. Le canal alpha n'apporte que du bruit si l'encodeur ne s'en est pas servi.

Rappel de la notation des combinaisons `zsteg` : `bX,canaux,bit,ordre`.

- `b1` : un bit par canal ;
- `rgb` : canaux rouge, vert, bleu (alpha ignoré) ;
- `lsb` : bit de poids faible d'abord ;
- `xy` : parcours des pixels de gauche à droite, ligne par ligne.

Sur une image de quelques centaines de pixels de côté, un bit par canal donne déjà une capacité de plusieurs dizaines de kilo-octets, largement suffisante pour un flag. C'est pourquoi le LSB brut est l'hypothèse la plus probable, avant même d'avoir testé : l'encodeur n'a pas eu besoin d'étaler le message ni de le compresser.

## Solution

### Balayage exhaustif

```bash
zsteg -a -v pico.flag.png
```

`-a` teste toutes les combinaisons connues, `-v` affiche le détail des candidats. La sortie révèle le flag sur la ligne étiquetée **`b1,rgb,lsb,xy`**.

### Extraction ciblée

Une fois la combinaison connue, on la demande explicitement :

```bash
zsteg -E "b1,rgb,lsb,xy" pico.flag.png
```

`-E` extrait la charge utile au lieu de la chercher dans toutes les méthodes ; c'est instantané comparé au balayage.

### Contrôle du résultat

La sortie doit commencer par le préfixe de flag de l'événement et se terminer par l'accolade fermante. Si elle ressemble à du binaire, c'est que le bit ou l'ordre de parcours est faux : on revient à la ligne du balayage qui contenait le motif lisible.

Un second outil confirme le plan de bits quand la sortie texte est ambiguë :

```bash
stegsolve pico.flag.png
```

L'outil graphique ne remplace pas le balayage, il sert à vérifier visuellement quel plan contient le message.

### Pourquoi ça marche

Les bits de poids faible d'un pixel ne changent sa couleur que d'une unité : les remplacer par les bits du message ne modifie pas l'image de façon perceptible. C'est ce qui rend la technique invisible à l'œil nu.

`zsteg` parcourt les canaux et recompose les octets dans l'ordre demandé. Dès que la combinaison et l'ordre de parcours correspondent à ceux de l'encodeur, les bits se réassemblent en ASCII lisible.

## Pièges

- **Commencer par un outil en ligne** : une seule combinaison testée, souvent avec l'alpha, et l'échec fait croire à une autre technique.
- **Ignorer `-a`** : les options par défaut ne couvrent pas toutes les combinaisons ; c'est le balayage complet qui tranche.
- **Se tromper d'ordre** : `xy` et `yx` donnent des octets différents ; le motif lisible indique le bon ordre.
- **Oublier les guillemets sur `-E`** : la combinaison contient des virgules, que le shell peut interpréter.
- **Confondre LSB et palette** : sur une image indexée, le message peut être dans la palette et non dans les pixels.

Flag validé sur la plateforme (valeur non conservée).
